Auth Flow — Registration and Login
Registration
The registration flow is a two-step wizard for new business onboarding. Step 1 — GSTIN verification: The user enters their 15-character GSTIN into a single input field. On blur or on a "Verify" button click, the frontend calls the backend which hits the GSTN verification API (via a third-party GSP such as Masters India or KnowYourGST). While the API call is in flight, show a loading skeleton over the form. On a successful response, the form populates with the fetched data and transitions to the full registration form. If the GSTIN is invalid, cancelled, or not found, show an inline error — do not proceed. Step 2 — Review and complete: The populated form shows two categories of fields. Non-editable fields — displayed as read-only styled inputs with a lock icon or a muted background — are: GSTIN, Legal Name (lgnm), Constitution of Business (ctb), GST Registration Date (rgdt), Principal Address (pradr), and State. These are rendered as <div> displays or readOnly inputs, never actual form inputs. GSTIN status and e-invoice applicability are shown as Badge components (Active in green, Cancelled in red) for information only and are never form fields. Editable fields the user must fill in are: Trade Name (pre-filled from tradeNam if returned by API, but editable because it appears on all invoices and may differ from the API value), Phone Number (mandatory, Indian mobile, used for WhatsApp notifications and OTP login), Email Address (mandatory, used for login), and Password with a confirm password field (minimum 8 characters, must include one number and one special character, validated with Zod). On submit, POST to /api/auth/register with all fields. The backend stores GSTIN-fetched fields directly from the API response — never from the client payload — to prevent tampering. After successful registration, redirect to the onboarding screen for business tier selection.
Login
Login is a single-screen form with two fields: identifier (email address or phone number — one input that accepts both, detected by format) and password. On submit, POST to /api/auth/login. On success, store the JWT access token in an httpOnly cookie (handled server-side) and redirect to /dashboard. On failure, show a generic "Invalid credentials" inline error — never specify whether the email or password was wrong. Provide a "Forgot password?" link below the form that initiates an OTP reset flow to the registered phone number via WhatsApp. The login page must have no sidebar, no navigation — a centered card layout matching the auth layout shell.
