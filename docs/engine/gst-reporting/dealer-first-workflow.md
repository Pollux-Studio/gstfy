# Proposed Dealer-First GST Workflow

## Objective

Gstfy should hide CA-level GST complexity from the dealer while preserving a complete review console for the business owner, accountant, or CA.

The product should answer one simple question for a dealer:

> What do I need to do today to keep my GST records ready?

The dealer should not need to understand reconciliation status codes, GSTR-2B file formats, ITC state transitions, or filing payload validation.

## Two Experiences

### Dealer Experience

The dealer sees a guided GST checklist:

1. **Record purchases**
2. **Confirm unusual purchases**
3. **Review items needing attention**
4. **Approve the monthly GST summary**

Dealer-facing language should use plain outcomes:

- Purchase matched
- Supplier bill not found
- Tax amount looks different
- This purchase may not qualify for credit
- Waiting for supplier update
- Ready for CA review

The dealer should not see `ELIGIBLE`, `DEFERRED`, `REJECTED`, `BOOKS_ONLY`, or `EXTERNAL_ONLY` as primary labels.

### CA/Accountant Experience

The CA console can expose the detailed workspace:

- Reconciliation rows and match confidence.
- Supplier and invoice differences.
- ITC eligibility decisions.
- Deferred and rejected records with reasons.
- Claim and reversal history.
- Exception queue.
- Filing review and filing-run controls.

The same business data is used in both experiences. The difference is the language, permissions, level of detail, and available actions.

## GSTR-2B Integration Model

### Important Distinction

GSTR-2B is generated by the GST system from supplier-filed data. Gstfy does not create the government GSTR-2B. Gstfy retrieves the available statement and reconciles it with purchase records.

The GST portal's advisory describes GSTR-2B as an auto-drafted, static ITC statement made available for each month, normally on the 14th of the succeeding month:

- [GSTN GSTR-2B Advisory](https://tutorial.gst.gov.in/offlineutilities/returns/GSTR2B/GSTR-2B_Advisory.pdf)

### Authorization

The dealer must authorize the connection. Saving a GSTIN is not enough. The integration should use an approved GST API, GSP, or ASP route.

The expected connection flow is:

1. Dealer enters and verifies the GSTIN.
2. Gstfy explains what data will be accessed and why.
3. Dealer enables GST portal API access when required.
4. Dealer authorizes the selected Gstfy/GSP application.
5. Dealer verifies an OTP when the GST session or provider requires it.
6. Gstfy records the authorization state and expiry without storing the dealer's GST password.

Zoho Books documents an API-access setup followed by GSTN username and OTP-based fetching. TallyPrime documents direct portal login from the application, OTP verification, and a limited login session. These are useful reference patterns, not a reason to copy their exact implementation:

- [Zoho Books GSTR-2B reconciliation](https://www.zoho.com/in/books/help/gst/gstr2b-reconcile.html)
- [TallyPrime GSTR-2B reconciliation](https://help.tallysolutions.com/gstr-2b-reconciliation/)

### Backend Sync Pipeline

```text
GST/GSP Authorization
        |
        v
Authorized GST Connector
        |
        v
Fetch GSTR-2B for GSTIN + Period
        |
        v
Validate and Normalize Source Data
        |
        v
Store Immutable Source Snapshot
        |
        v
Match Against Posted Purchase Tax Records
        |
        +--> Matched records
        +--> Dealer attention tasks
        +--> CA exceptions
        |
        v
Calculate Reviewed ITC Dataset
        |
        v
Generate GSTR-1/GSTR-3B Reports
```

The connector should support:

- One or more GSTINs per business.
- Monthly period synchronization.
- Manual `Sync now` initiated by a permitted user.
- Authorization expiry and reconnect handling.
- Retry with backoff for transient provider failures.
- Idempotent synchronization so the same statement cannot duplicate records.
- Source revisions and regenerated statements.
- Audit history for who connected, synced, or re-synced a GSTIN.

### Dealer-Facing Connection States

Use simple states:

- **Connected:** GSTFY is ready to sync GST data.
- **Syncing:** GSTFY is retrieving this month's statement.
- **Waiting:** The statement is not available for the selected period yet.
- **Reconnect required:** Authorization or session access has expired.
- **Sync issue:** GSTFY could not complete the sync and will explain the next step.

Manual JSON upload should be a CA-only fallback until the live connector is available. It should not be the primary dealer workflow.

## Reconciliation Rules

Reconciliation should run automatically after both sides are available:

- Posted purchase tax records from Gstfy books.
- GSTIN and invoice details from the GSTR-2B snapshot.

The matching keys should prioritize:

1. GSTIN of the supplier.
2. Normalized invoice/document number.
3. Invoice/document date.
4. Taxable value and tax components.

Supplier name can support review but should not determine a match by itself.

The engine should preserve both book and external values. It should store differences rather than overwriting one source with the other.

### Dealer Result Mapping

| Technical result | Dealer message | CA action |
|---|---|---|
| Exact/strong match | Purchase matched | No action unless selected for review |
| Books only | Supplier bill not found in GST data | Contact supplier or defer review |
| External only | GST data has a purchase not recorded in Gstfy | Create or verify purchase |
| Tax/value mismatch | Tax amount needs attention | Compare invoice and resolve |
| Duplicate | Possible duplicate purchase | Review before credit is considered |
| Manual review | GSTFY needs help deciding | CA reviews manually |

## ITC Decision Model

ITC should be determined by rules first and human review second. The system must not mark every matched invoice as claimable automatically.

The rule engine should consider, at minimum:

- Valid tax invoice or other eligible document.
- Supplier GSTIN and document details.
- Goods or services received.
- Business use.
- Presence and availability in the relevant GST data.
- Whether the purchase is blocked or restricted under applicable GST rules.
- Reconciliation differences.
- Duplicate or cancelled records.
- Previously claimed, reversed, or remaining amounts.

The rules should produce an explanation and a recommended outcome. The final claim dataset must be auditable.

### Internal ITC States

The detailed internal state machine can remain:

```text
NOT_REVIEWED
    |
    +--> ELIGIBLE --------> CLAIMED --------> REVERSED
    |
    +--> PARTIALLY_ELIGIBLE -> CLAIMED
    |
    +--> DEFERRED ---------> ELIGIBLE
    |
    +--> INELIGIBLE
    |
    +--> REJECTED
```

The application should distinguish these meanings:

- **Eligible:** The rule checks passed and the amount may be included in the claim review.
- **Partially eligible:** Only a calculated portion can be considered.
- **Deferred:** The item may be claimable later, but should not be included in the current claim decision.
- **Rejected/Ineligible:** The item should not be claimed, with an explanation and audit reason.
- **Claimed:** The amount was included in the approved claim dataset.
- **Reversed:** A prior claim was subsequently reversed.

`Deferred` is a workflow decision, not a way to hide a mismatch. Mismatches should remain visible with a reason. `Rejected` should not be used merely because a supplier has not uploaded an invoice; that situation usually needs correction or deferral.

## Monthly Dealer Flow

```text
1. Dealer records purchases during the month
2. GSTFY syncs GSTR-2B when available
3. GSTFY matches purchase records automatically
4. GSTFY creates only the small set of dealer tasks
5. Dealer confirms simple questions
6. CA reviews exceptions and ITC recommendations
7. GSTFY generates GSTR-1 and GSTR-3B summaries
8. Dealer/CA approves the review
9. Filing workflow proceeds through the authorized integration or GST portal
```

The dealer should receive one monthly completion state, for example:

```text
GST preparation: 80% complete
2 purchases need your confirmation
Your CA has 1 item to review
```

## Recommended Product Changes

### Dealer GST Home

Replace the current multi-tab default screen with:

- Current month and GSTIN.
- GST connection status.
- Completion progress.
- Purchases needing dealer confirmation.
- Items waiting for supplier correction.
- CA review status.
- Generate/prepare summary action.

### Advanced GST Workspace

Keep the current detailed tabs behind an `Accountant view` or a role permission:

- Reconciliation.
- ITC review.
- Filing review.
- GSTR-1.
- GSTR-3B.
- Filing history.
- Exceptions.

### Permissions

- Dealer: record purchases, answer guided questions, view summaries, approve when allowed.
- Accountant/CA: reconcile, defer, reject, claim, reverse, resolve exceptions, and manage filing runs.
- Owner: configure GSTIN connection and approve access.

## Implementation Phases

### Phase 1: Product Boundary

- Keep current detailed GST workspace working for CA/operator users.
- Add a dealer-friendly GST overview route or mode.
- Hide technical status labels from the dealer surface.
- Keep manual import out of the dealer UI.

### Phase 2: Connector Foundation

- Select and contract with a GST GSP/ASP or validate direct API eligibility.
- Define authorization, consent, OTP, token, and expiry behavior.
- Add encrypted connection records per GSTIN.
- Add connector health and audit events.

### Phase 3: Automated Synchronization

- Add a backend sync job for available periods.
- Add idempotent source snapshots and revision handling.
- Add manual sync for permitted users.
- Add retry, error, and reconnect states.

### Phase 4: Rule-Based ITC Review

- Implement server-side eligibility checks.
- Protect claim amounts by CGST, SGST, IGST, and cess.
- Enforce valid state transitions and concurrency control.
- Store explanations and immutable audit events.

### Phase 5: Dealer UX

- Build the guided monthly checklist.
- Convert technical exceptions into plain-language tasks.
- Add CA assignment and review handoff.
- Add approval before report generation or filing.

## Key Principle

Gstfy should automate the data collection and first-level checks, but it should not silently make an irreversible tax decision. The dealer gets clarity, the CA gets control, and every recommendation remains explainable and auditable.
